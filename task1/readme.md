# Задача 1. Архитектурное решение: Повышение безопасности системы BionicPRO


## 1. Цели архитектурного решения

1. Исключить передачу access- и refresh-токенов на фронтенд.
2. Унифицировать доступ ко всем сервисам BionicPRO через запрос учётных данных из внешнего IdP, расположенного в стране присутствия.
3. Обеспечить локализацию хранения медицинских данных.
4. Поддерживать аутентификацию через различные внешние удостоверяющие службы, сохраняя единый пользовательский опыт.
5. Гарантировать, что пользователь может запрашивать только отчёты.

## 3. Архитектурное решение

### 3.1. Backend For Frontend (BFF) — безопасная точка входа

Все клиентские приложения (мобильное приложение, интернет-магазин) взаимодействуют только с **BFF Proxy**, расположенным на том же домене.  
BFF реализует поток **Authorization Code Grant + PKCE** на серверной стороне:

- Клиент перенаправляется на IdP (Keycloak) для аутентификации.
- После успешного входа IdP возвращает **authorization code** на BFF.
- BFF обменивает code на access_token, refresh_token и id_token, используя `client_secret`, который никогда не покидает сервер.
- **Токены не передаются во фронтенд.** Вместо этого BFF сохраняет их в серверной сессии (Redis) и выдаёт клиенту **httpOnly, Secure, SameSite=Strict сессионную куку**.
- Все последующие запросы к внутреннему API BFF выполняет от имени пользователя, добавляя access_token в заголовок Authorization.

Это исключает возможность кражи токенов через XSS или вредоносные расширения браузера.

### 3.2. Федеративная аутентификация с локальным хранением учётных данных

Центральным брокером аутентификации выступает **Keycloak**, развёрнутый в контуре BionicPRO.  
Для каждой страны Keycloak настраивает **Identity Federation** с соответствующим национальным IdP.

- Пользователь аутентифицируется в привычной системе своей страны.
- Учётные данные (логины, пароли, личная информация) **не хранятся** в Keycloak.
- Keycloak получает только минимально необходимые утверждения (claims): идентификатор пользователя, роль, страна.
- Медицинские данные и телеметрия хранятся **в региональных базах данных**, физически размещённых в ЦОД соответствующей страны. API маршрутизирует запросы в нужную БД на основе атрибута `country` из JWT.

### 3.3. Аутентификация устройства

- Чип протеза взаимодействует с API напрямую по протоколу **Client Credentials Grant**.  
- Секрет клиента записывается в чип на этапе производства и может обновляться по защищённому каналу. Токены для устройств имеют короткий срок жизни и ограниченный набор разрешений (только отправка телеметрии и приём команд).

### 3.4. Безопасность токенов и сессий

- API проверяет подпись JWT через **JWKS** (JSON Web Key Set), предоставляемый Keycloak.
- Refresh-токены хранятся в серверной сессии BFF и **ротируются** при каждом использовании, что делает невозможным их повторное применение.
- Для BFF используется отдельный `client_id` с типом `confidential`, для устройств - `confidential` с аутентификацией по секрету.
- Все внутренние запросы между сервисами выполняются по mTLS или внутри защищённой сети.

## 5. Соответствие целям

- **Устранение уязвимости SSO**: токены никогда не попадают в браузер или мобильное приложение, используются только httpOnly куки.
- **Локализация данных**: данные хранятся и обрабатываются в стране пользователя; маршрутизация определяется по стране из JWT.
- **Поддержка разных IdP**: федерация через Keycloak позволяет легко подключать новые национальные системы.
- **Разграничение доступа к отчётам**: API фильтрует данные по `sub` (идентификатору пользователя) из валидированного JWT, исключая возможность доступа к чужим данным.

## 6. Дальнейшие шаги

- Реализовать BFF Proxy на базе Spring Cloud Gateway или OAuth2-Proxy.
- Настроить региональные кластеры БД и синхронизацию справочных данных при необходимости.
- Внедрить централизованный мониторинг и аудит доступа к медицинским данным.
